# Development Log - RFID Protocol Refactoring and Bug Fixes

**Date:** December 18, 2025
**Task:** Refactor to polling-based commands and fix tag detection issues
**Status:** ✓ Complete

## Objective

Address reliability issues in continuous inventory mode (0x89) by migrating to polling-based single inventory commands (0x8B), and fix critical parsing bugs causing false positives and data corruption.

## Problem Analysis

### Issues with Continuous Mode (0x89)
1. Unpredictable timing - tags streamed asynchronously with no rate control
2. Resource intensive - continuous RF transmission and data processing
3. Difficult debugging - interleaved tag and completion packets
4. No read rate control

### Tag Detection Issues
1. False positives - invalid detections with RSSI=0, all-zero EPCs
2. First read truncation - initial frames incomplete/inconsistent
3. Incorrect EPC length - calculated from buffer size instead of PC word
4. Wrong RSSI position - parsing error due to incorrect EPC length calculation

## Solution 1: Polling-Based Architecture

### Command Migration: 0x89 → 0x8B

Switched from continuous real-time inventory to polling-based single inventory.

**Command 0x8B: Customized Inventory**
- Status: Undocumented in R300 protocol V2.2
- Source: Reverse-engineered from UHFDemo v3.62 C# implementation
- Purpose: EPC C1G2 Gen2 session and target control
- Format: `[0xA0][0x06][Addr][0x8B][Session][Target][Round][Check]`

**Parameters:**
- Session: 0x00-0x03 (S0, S1, S2, S3)
- Target: 0x00-0x01 (Inventoried flag A/B)
- Round: 0x01-0xFF (Q value)

**Current Configuration:** Session 0x00 (S0 - volatile), Target 0x00 (Flag A), Round 0x01 (Q=1, optimal for single tag)

### Architecture Changes

**Configuration Added:**
- Default read interval: 250ms
- Minimum read interval: 50ms

**Updated API:**
- Old: `esp_err_t rfid_reader_start_inventory(rfid_tag_callback_t callback);`
- New: `esp_err_t rfid_reader_start_inventory(rfid_tag_callback_t callback, uint32_t interval_ms);`

**UART RX Task Refactor:**
- Before (event-driven): Wait for continuous tag stream, process tags, auto-restart on completion
- After (polling-based): Send 0x8B at configured interval, wait for response with timeout, process tag, delay until next poll, repeat

**Benefits:**
1. Configurable read rate (50ms to any interval)
2. Predictable timing and resource usage
3. Better control over RF transmission duty cycle
4. Simpler protocol flow
5. Easier debugging with discrete read operations

## Solution 2: Tag Detection Validation

### RSSI Validation
**Problem:** RSSI=0 causing false positives
**Solution:** Multi-layer validation with valid range check (31-98 per R300 protocol)
- RSSI to dBm conversion: Range 31-98 → -99 to -31 dBm
- Formula: `dBm = rssi - 130`
- Typical working range: 40-70 (approx -90 to -60 dBm)

### EPC Validation
**Added checks:**
1. Minimum length: 8 bytes (EPC C1G2 standard requirement)
2. All-zero detection: Reject EPCs with all 0x00 bytes
3. Frame length validation: Minimum 17 bytes for valid tag response

### UART Timeout Fix
**Problem:** First read often truncated or incomplete
**Root Cause:** 10ms timeout insufficient for complete frame transmission at 115200 baud
**Solution:**
- Increased timeout: 10ms → 50ms
- Added incomplete frame detection using Len field
- Implemented frame completion logic with retry
**Result:** Reliable complete frame reception on first read

## Solution 3: Parsing Bug Fixes

### Critical Fix: EPC Length Calculation

**Old (WRONG):** `uint16_t epc_len = len - 11;` (from total buffer length)
**Problem:** Includes completion packet and extra bytes

**New (CORRECT):** Extract from PC word per EPC C1G2 Gen2 standard
- Extract PC word from data[5:6]
- Get EPC word count from PC bits 15-11
- Convert words to bytes (multiply by 2)

**Result:** Before: 24 bytes (incorrect) → After: 12 bytes (correct)

### RSSI Byte Position Fix

**Old (WRONG):** `uint8_t rssi = data[len - 2];` (wrong position due to incorrect EPC length)
**New (CORRECT):** `uint8_t rssi = data[7 + epc_len];` (after PC(2) + EPC(N))

**Frame Structure:** `[Head][Len][Addr][Cmd][Freq_Ant][PC(2)][EPC(N)][RSSI][Check]`

### Completion Packet Handling

**Problem:** Parser processed entire buffer including completion packet appended after tag data
**Solution:** Extract actual packet length from Len field, process only tag packet, ignore completion packet

## Technical Insights

### EPC C1G2 Gen2 Protocol
- PC word bits 15-11 encode EPC word count
- Session persistence affects tag re-detection
- Session S0 volatile, resets quickly (ideal for repeated reads)
- Target flag (A/B) controls inventory state

### R300 Module Behavior
- 0x8B more predictable than 0x89 for single-tag scenarios
- Response timing consistent: ~20-30ms per command
- Completion packet sometimes appended to tag packet
- RSSI values reliable indicator of read quality

### Frame Reception
- 50ms timeout sufficient for complete frames at 115200 baud
- Incomplete frame detection via Len field essential
- Frame completion retry improves reliability significantly

## Key Takeaways

1. Critical command (0x8B) completely undocumented in official spec
2. Reference implementation (C# code) provided missing protocol details
3. Multi-layer validation prevents false positives
4. Understanding EPC Gen2 standard critical for correct parsing
5. UART timing significantly impacts reliability
6. Polling provides better control for single-tag scenarios

## Performance Comparison

**Before (0x89 continuous):** Unpredictable timing, ~30-50ms per round (uncontrolled), auto-restart complexity, difficult to debug

**After (0x8B polling):** Configurable interval (default 250ms), predictable timing, simple start/stop, easy to debug discrete operations
