# Development Log - Network Resilience Architecture

**Date:** December 24, 2025
**Task:** Design and implement offline event logging system for network outage resilience

## Objective

Design and implement an offline event logging system for the ESP32 lighthouse units that provides resilient operation during network outages, with automatic event replay upon connectivity restoration.

---

## 1. Requirements Analysis

### Operational Requirements

| Requirement           | Target               | Rationale                                     |
| --------------------- | -------------------- | --------------------------------------------- |
| Outage tolerance      | 2-3 hours            | Typical facility network outage duration      |
| Real-time performance | Non-blocking         | RFID detection must not be delayed by storage |
| Power safety          | Survive power cycles | Flash-based persistence required              |
| Event rate            | 2-5 events/second    | Peak attendance periods                       |

### Storage Capacity Estimation

**Conservative calculation:**
- Peak rate: 5 tags/second
- Target duration: 3 hours = 10,800 seconds
- Events needed: 54,000 events
- Record size: 48 bytes (optimized with alignment)
- Storage needed: ~2.6 MB

## 2. Hardware Analysis

### ESP32-WROOM-32 Memory Resources

**Internal SRAM (520 KB):**
- Volatile - does NOT survive power loss
- Shared across both cores
- Needed for active operations
- **Verdict:** Unsuitable for persistent storage

**Internal Flash (4 MB):**
- Non-volatile - survives power cycles
- Available after firmware: ~2 MB
- Wear leveling via filesystem
- **Verdict:** Suitable for event storage

**External Options Evaluated:**
- PSRAM (2 MB): Volatile - rejected
- External SPI Flash: Adds hardware complexity - deferred

### Decision: Internal Flash with LittleFS

**Rationale:**
1. No additional hardware required
2. Sufficient capacity for 2-3 hour outages
3. Power-safe filesystem with wear leveling
4. Proven reliability in ESP32 ecosystem

```csv
# Name,         Type,  SubType,    Offset,    Size,    Flags
```

### Memory Layout Breakdown

```
Address Range      Size      Partition          Purpose
0x000000-0x008000  32 KB     Bootloader         ESP-IDF managed
0x008000-0x009000  4 KB      Partition Table    Partition metadata
0x009000-0x00F000  24 KB     NVS                WiFi credentials, settings
0x00F000-0x010000  4 KB      PHY Init           RF calibration data
0x010000-0x110000  1 MB      Factory App        Compiled firmware
0x110000-0x310000  2 MB      offline_events     RFID Event Storage (LittleFS)
0x310000-0x400000  960 KB    Reserved           Future expansion
```

### Capacity Verification

- Partition size: 2,097,152 bytes (2 MB)
- Event record: 48 bytes (aligned)
- Maximum events: **43,690 events**
- Coverage @ 5 events/sec: **2.43 hours**
- Coverage @ 3 events/sec: **3.65 hours**

## 4. Event Record Structure

Designed 48-byte aligned event record for optimal flash performance:

```c
typedef struct {
    uint64_t timestamp_ms;      // 8 bytes - milliseconds since boot
    uint32_t rtc_timestamp_s;   // 4 bytes - unix time (set during sync)
    uint8_t  epc[24];           // 24 bytes - EPC buffer (96-bit max)
    uint8_t  epc_length;        // 1 byte - actual EPC length
    uint8_t  reader_id;         // 1 byte - which reader
    int8_t   rssi_dbm;          // 1 byte - signal strength in dBm
    uint8_t  flags;             // 1 byte - status flags
    uint32_t crc32;             // 4 bytes - data integrity check
    uint8_t  reserved[4];       // 4 bytes - alignment padding
} offline_event_t;              // Total: 48 bytes
```

## 5. Storage Architecture

### Ring Buffer Implementation

- Single LittleFS file with fixed record capacity
- Write pointer: RTC memory (survives deep sleep)
- Read pointer: Advanced after successful MQTT transmission
- Overflow: Oldest events overwritten (graceful degradation)

### Key Features

| Feature        | Implementation                    |
| -------------- | --------------------------------- |
| Async writes   | FreeRTOS task with 64-event queue |
| Thread safety  | Mutex-protected file operations   |
| Data integrity | CRC32 per record                  |
| Power safety   | LittleFS journaling               |

## 6. Synchronization Strategy

### Event Replay Timeline

```
T+0s:    Network restoration detected
T+1s:    Continue real-time detection (separate queue)
T+30s:   Begin replaying cached events (grace period)
         - Throttle: max 10 events/second
         - Add 'offline' flag to MQTT payload
T+180s:  Transition to real-time mode
```

### MQTT Payload Differentiation

**Real-time events:**
```json
{
  "type": "attendance",
  "timestamp": 1703251200000,
  "epc": "E2003A4F03E57CB42EB9",
  "offline": false
}
```

**Offline replay events:**
```json
{
  "type": "attendance",
  "timestamp": 1703250900000,
  "epc": "E2003A4F03E57CB42EB9",
  "offline": true,
  "replay_time": 1703251200000
}
```

## Technical Insights

### LittleFS vs SPIFFS

| Feature           | LittleFS              | SPIFFS            |
| ----------------- | --------------------- | ----------------- |
| Power-loss safety | Yes (journaling)      | No                |
| Wear leveling     | Dynamic               | Static            |
| Directory support | Yes                   | No                |
| Performance       | Better for sequential | Better for random |
| **Choice**        | **LittleFS**          | -                 |

### Flash Wear Considerations

- Typical flash: 100K erase cycles per sector
- LittleFS wear leveling distributes writes
- At 5 events/sec, theoretical flash life: 10+ years
- Acceptable for production deployment
