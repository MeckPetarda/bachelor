# Development Log - WiFi Provisioning System

**Date:** January 5–7, 2026
**Task:** Implement WiFi provisioning system for lighthouse devices

## Objective

Replace compile-time WiFi credentials with a runtime provisioning system allowing field configuration via captive portal. Credentials must be stored securely, survive power cycles, and integrate without disrupting RFID operations.

---

## 1. Design Decisions

| Decision         | Choice                  | Rationale                                                       |
|------------------|-------------------------|-----------------------------------------------------------------|
| Storage location | Dedicated NVS partition | Isolates config from event data, reduces corruption risk        |
| Encryption       | AES-128-ECB             | Hardware-accelerated on ESP32 (TRM Section 14)                  |
| Setup trigger    | 5-second button hold    | Prevents accidental entry, coexists with statistics short-press |
| Provisioning UI  | Minimal HTML form       | Reduces firmware size, fast loading                             |
| Mode transition  | Reboot to enter setup   | Clean state, no interference with running tasks                 |

**Reference:** `tasks/wifi_provisioning.md` Part 6

---

## 2. State Machine

```
UNCONFIGURED ──(5s button)──► SETUP_REQUESTED ──(reboot)──► AP_ACTIVE
                                                               │
                    ┌──────────(timeout)───────────────────────┤
                    │                                          │
                    ▼                              (creds submitted)
              UNCONFIGURED ◄──(fail)── CONNECTING ──(success)──► CONNECTED
```

Setup mode detected via RTC memory flag that survives soft reset. LED blinks at 1Hz during AP mode, 4Hz while connecting, solid when connected.

---

## 3. Implementation Summary

### Phase 1: Storage Layer

Created dedicated `nvs_settings` partition (16KB) with encrypted credential storage:

- **Configured flag:** 1 byte at offset 0
- **Encrypted SSID:** 32 bytes (AES-128 block)
- **Encrypted password:** 64 bytes (AES-128 block)
- **Reserved for MQTT:** 30 bytes (future use)

Encryption uses ESP32 hardware AES accelerator via mbedTLS. Device-specific 16-byte key defined in configuration header. Credentials never logged in plaintext.

**Reference:** ESP32 TRM Section 14 (AES Accelerator)

### Phase 2: State Machine & Button Integration

Modified BUTTON2 handling to detect 5-second hold for setup mode while preserving short-press statistics functionality. State machine manages transitions between unconfigured, AP active, connecting, and connected states.

Boot sequence modified to check for setup request flag and block RFID initialization until WiFi connected.

### Phase 3: HTTP Server & Web Provisioning

Access point broadcasts "Lighthouse-Setup" network. HTTP server on port 80 serves minimal HTML form for credential entry. On submission:

1. Validate input lengths (SSID: 1–31, password: 8–63 per WPA2)
2. Attempt STA connection with 10-second timeout
3. If successful: encrypt and save to NVS, return success
4. If failed: return error, form re-appears for retry

## 4. Issues Resolved

### NVS Handle Naming Conflict

Variable name `nvs_handle` conflicted with ESP-IDF typedef. Renamed to `settings_storage_nvs_handle`.

### WiFi Event Type Conflict

Custom `wifi_event_t` enum conflicted with ESP-IDF's own type. Renamed to `wifi_prov_event_t`.
