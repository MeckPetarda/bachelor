# Development Log - Yanpodo RU6500 RFID Reader Setup

**Date:** December 6, 2024  
**Task:** Establish communication with Yanpodo RU6500 UHF RFID reader/writer for tag initialization and testing  
**Status:** ✓ Complete - Reader successfully operational

## Objective

Set up the Yanpodo RU6500 desktop UHF RFID reader to read and initialize RFID tags for later integration testing. This reader is not part of the final device but serves as a development tool for tag preparation and verification.

## Initial Problem

Device was physically responsive to RFID tags (LED blink, audible beep) but produced no data output to the host system. Multiple interface points were attempted:
- `/dev/input/event18` - No data
- `/dev/hidraw3` - No data
- USB control transfers - Device busy (kernel HID driver claimed)

## Investigation Process

### 1. Device Detection
Used `dmesg` and USB enumeration to confirm device presence:
- Vendor ID: `0x1A86`
- Product ID: `0xE010`
- Identified as `SWUSB_HID` keyboard HID device
- Kernel recognized as hidraw and input event devices

### 2. Interface Exploration
Created Python scripts using `pyusb` to probe USB device directly. Encountered "Resource busy" errors due to kernel HID driver holding the device. This indicated the device was functional but not accessible through raw USB.

### 3. HID Device Discovery
Attempted reading from `/dev/usb/hiddev0` (HID device interface, different from hidraw or input event). Initial `cat` command revealed binary data streaming during tag scans.

### 4. Data Format Analysis
Captured raw HID data and analyzed structure:
```
030000ff20000000030000ff43000000030000ff54000000...
```

Determined format: 64-byte chunks containing 8 reports of 8 bytes each
- Byte 0: Report type (0x03 for keyboard)
- Bytes 1-3: Reserved
- Byte 4: **Value byte (actual data)**
- Bytes 5-7: Reserved

### 5. Data Extraction & Decoding
Wrote decoder to extract value bytes (byte 4 of each 8-byte report) and convert to hexadecimal. Successfully extracted complete RFID tag EPC.

## Solution

Found working interface: `/dev/usb/hiddev0`

Working approach:
1. Read 64-byte chunks from hiddev0
2. Extract 8 value bytes per chunk (every 8 bytes, take byte 4)
3. Accumulate bytes until empty chunks indicate tag completion
4. Output complete tag as hex string

## Test Results

Successfully read RFID tag:
- **EPC (hex):** `2043541C014501D3042509097862010F0101E217570D59237023F4AC`
- **Length:** 28 bytes
- **Detection:** Reliable (device correctly detects tag presence with visual/audio feedback)
- **Data Quality:** Complete and consistent across multiple reads

## Technical Notes

### Why `/dev/usb/hiddev0` Works
- Hiddev is the HID device interface (not keyboard emulation like hidraw)
- Accessible without kernel driver conflict
- Provides raw HID reports with embedded data
- Suitable for non-keyboard HID devices

### Device Mode
Device is in "Answer Mode" or passive reading mode - reports tag data only when tags are presented, not on demand via queries. This is the expected behavior for this model.

### Data Format
Tag EPC is delivered as a sequence of raw bytes (0x00-0xFF), not ASCII. Displaying as hexadecimal preserves data integrity for tag verification and programming.

## Integration Notes

This reader is a development tool only. For final system integration:
- Reader can be reconfigured to RS232 serial mode (contact manufacturer)
- Final device will use embedded UHF RFID module with direct MCU interface
- Reader serves current purpose: tag initialization, verification, and testing

## Lessons Learned

1. Kernel HID driver can block direct USB access - hiddev/hidraw interfaces may be necessary
2. Raw data analysis and format reverse-engineering was effective when documentation unavailable
3. Simple debug scripts often more useful than complex abstractions during troubleshooting
4. Testing with actual hardware reveals interface quirks better than datasheet alone
