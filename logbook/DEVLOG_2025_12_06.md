# Development Log - Yanpodo RU6500 RFID Reader Setup

**Date:** December 6, 2024
**Task:** Establish communication with Yanpodo RU6500 UHF RFID reader/writer

## Objective

Set up Yanpodo RU6500 desktop UHF RFID reader for tag preparation and verification. This is a development tool, not part of the final device.

## Problem

Device responded physically to tags (LED blink, beep) but produced no data output to host system. Attempted `/dev/input/event18`, `/dev/hidraw3`, and USB control transfers - all failed.

## Investigation

### Device Identification
- Vendor ID: `0x1A86`
- Product ID: `0xE010`
- Detected as `SWUSB_HID` keyboard HID device
- Kernel claimed device, blocking raw USB access

### Solution Discovery
Found working interface: `/dev/usb/hiddev0` (HID device interface, different from hidraw or input event)

### Data Format
64-byte chunks containing 8 reports of 8 bytes each:
- Byte 0: Report type (0x03 for keyboard)
- Bytes 1-3: Reserved
- Byte 4: **Value byte (actual data)**
- Bytes 5-7: Reserved

### Extraction Method
1. Read 64-byte chunks from hiddev0
2. Extract byte 4 from each 8-byte report
3. Accumulate until empty chunks indicate tag completion
4. Output as hex string

## Results

Successfully read RFID tag:
- **EPC:** `2043541C014501D3042509097862010F0101E217570D59237023F4AC` (28 bytes)
- Reliable detection with consistent data across multiple reads

## Technical Notes

- Hiddev provides raw HID reports without kernel driver conflict
- Device operates in "Answer Mode" - reports tags only when presented, not on demand
- Tag EPC delivered as raw bytes (0x00-0xFF), not ASCII
- Reader can be reconfigured to RS232 for production use

## Key Takeaways

1. Kernel HID driver can block direct USB access - hiddev/hidraw interfaces necessary
2. Raw data analysis effective when documentation unavailable
3. Simple debug scripts more useful than complex abstractions during troubleshooting
