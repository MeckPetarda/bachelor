# Development Log - Reader Handshake & Power Control Planning

**Date:** December 25, 2025
**Task:** Design comprehensive reader initialization and power monitoring system

## Objective

Replace passive error handling with active reader health verification. Implement handshake verification and power monitoring to provide precise failure diagnostics before attempting RFID operations.

---

## 1. Problem Analysis

### Current Limitations

The existing implementation produces only a warning when reader communication fails at startup. This passive approach has several issues:

| Problem | Impact |
|---------|--------|
| No active verification | Scanning attempted on unresponsive reader |
| Ambiguous errors | Cannot distinguish power vs communication failure |
| No remote diagnostics | MQTT health reports lack reader status |
| Manual intervention required | User must physically inspect hardware |

### Solution Overview

Implement three-layer verification:
1. **Power rail sensing** - Hardware-level power status
2. **Handshake verification** - Firmware communication test
3. **State machine** - Structured state tracking with clear transitions

## 2. Handshake Verification Design

### Command Selection: `get_firmware_version` (0x72)

Selected the `get_firmware_version` command for handshake verification:

**Command Format:**
```
TX: [0xA0] [0x03] [0x01] [0x72] [Check]
RX: [0xA0] [0x05] [0x01] [0x72] [Major] [Minor] [Check]
```

**Rationale:**
- Lightweight command (no RF operations)
- Fast response (~10ms typical)
- Returns useful diagnostic info (firmware version)
- Documented in R300 Protocol V2.2, Section 2.1.3

### Verification Points

Handshake performed at three critical points:

| Trigger | Purpose |
|---------|---------|
| System startup | Verify reader ready before configuration |
| Power-on events | Confirm reader responsive after power cycle |
| Periodic (60s) | Background health monitoring |

## 3. Power Monitoring Architecture

### Dual Power Rail Sensing

Implemented two-point power monitoring to distinguish failure modes:

```
                    ┌──────────────┐
    3.3V Supply ────┤ GPIO 4 sense ├───┬─── NPN Transistor ───┬─── Reader Module
                    └──────────────┘   │     (BC337)          │
                                       │                      │
                             Aux Supply│              ┌───────┴────────┐
                               Sense   │              │ GPIO 27 sense  │
                                       │              │ (Reader Power) │
                                       │              └────────────────┘
                                       │
                              ┌────────┴────────┐
                              │ GPIO 26 control │
                              │ (Active HIGH)   │
                              └─────────────────┘
```

### GPIO Assignments

| GPIO | Pin | Function | Direction | Notes |
|------|-----|----------|-----------|-------|
| GPIO 4 | 25 | Aux 3.3V supply sense | Input | Before transistor switch |
| GPIO 26 | 19 | Transistor control | Output | Active HIGH for BC337 |
| GPIO 27 | 32 | Reader power sense | Input | After transistor switch |

### Transistor Control Design

**Decision:** Replaced relay concept with NPN transistor

**Component:** BC337 NPN transistor
- Collector current: 500mA (sufficient for reader)
- Switching speed: <100ns (vs relay ~10ms)
- Control: Active HIGH via GPIO 26

**Benefits:**
- Faster switching than mechanical relay
- No contact bounce issues
- Lower power consumption
- More reliable long-term

## 4. State Machine Design

### Reader States

```c
typedef enum {
    RFID_STATE_SUPPLY_DOWN,           // Aux rail missing - hardware failure
    RFID_STATE_RELAY_CONTROL_ERROR,   // Transistor not switching correctly
    RFID_STATE_POWERED_OFF,           // Normal idle state
    RFID_STATE_STARTUP_PENDING,       // Powered, waiting for boot
    RFID_STATE_RESPONSIVE,            // Handshake successful
    RFID_STATE_UNRESPONSIVE,          // Powered but no response
} rfid_state_t;
```

### State Transition Diagram

```
                          ┌─────────────────┐
                          │  SUPPLY_DOWN    │◄───── Aux rail LOW
                          └────────┬────────┘
                                   │ Aux rail restored
                                   ▼
                          ┌─────────────────┐
       ┌──────────────────│  POWERED_OFF    │◄───── Deactivation
       │                  └────────┬────────┘
       │                           │ Activation trigger
       │                           ▼
       │                  ┌─────────────────┐
       │ Reader power     │ RELAY_CONTROL   │◄───── Transistor ON but
       │ rail stays LOW   │    _ERROR       │       reader power LOW
       │                  └─────────────────┘
       │
       │                           │ Reader power HIGH
       │                           ▼
       │                  ┌─────────────────┐
       │                  │ STARTUP_PENDING │ Grace period: 500ms
       │                  └────────┬────────┘
       │                           │
       │              ┌────────────┴────────────┐
       │              │                         │
       │              ▼                         ▼
       │    ┌─────────────────┐       ┌─────────────────┐
       │    │   RESPONSIVE    │       │  UNRESPONSIVE   │
       │    │ (Handshake OK)  │       │ (Timeout/Error) │
       │    └─────────────────┘       └─────────────────┘
       │              │                         │
       └──────────────┴─────────────────────────┘
                      Deactivation
```

## 5. Diagnostic Matrix

### Error State Identification

| Aux Rail | Transistor | Reader Power | State | Diagnosis |
|----------|------------|--------------|-------|-----------|
| LOW | - | - | SUPPLY_DOWN | Main 3.3V supply failure |
| HIGH | HIGH | LOW | RELAY_CONTROL_ERROR | Transistor not switching |
| HIGH | LOW | LOW | POWERED_OFF | Normal idle (expected) |
| HIGH | HIGH | HIGH | STARTUP_PENDING → RESPONSIVE/UNRESPONSIVE | Awaiting handshake |

### Actionable Error Messages

```c
const char* rfid_state_to_string(rfid_state_t state) {
    switch (state) {
        case RFID_STATE_SUPPLY_DOWN:
            return "Auxiliary 3.3V supply unavailable";
        case RFID_STATE_RELAY_CONTROL_ERROR:
            return "Transistor ON but reader power rail down";
        case RFID_STATE_POWERED_OFF:
            return "Reader power off (normal idle)";
        case RFID_STATE_STARTUP_PENDING:
            return "Reader powering up, awaiting boot";
        case RFID_STATE_RESPONSIVE:
            return "Reader responsive";
        case RFID_STATE_UNRESPONSIVE:
            return "Reader powered but not responding";
        default:
            return "Unknown state";
    }
}
```

## 6. Health Metrics Structure

### Extended Health Data

```c
typedef struct {
    // Timing
    uint32_t last_check_ms;
    uint32_t state_change_time_ms;

    // Firmware info
    uint8_t fw_major;
    uint8_t fw_minor;

    // Error tracking
    esp_err_t last_error;
    char last_error_msg[64];

    // Power status
    bool aux_supply_present;       // GPIO 4 - before transistor
    bool reader_power_present;     // GPIO 27 - after transistor
    bool transistor_control_ok;    // Control signal working

    // State
    rfid_state_t current_state;
    bool is_responsive;
} rfid_health_t;
```

## 10. PIR Sensor Conflict Resolution

**Issue:** GPIO 2 was previously allocated to PIR motion sensor

**Resolution:** PIR sensor functionality disabled to free GPIO for power monitoring

**Rationale:**
- PIR auto-scanning feature was already commented out
- Motion detection not critical for current deployment
- Power monitoring provides more value for diagnostics

**Changes:**
- Commented out PIR initialization in `gpio_init()`
- Disabled `process_pir()` function
- Updated help text to indicate PIR is disabled
