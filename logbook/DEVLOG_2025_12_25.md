# Development Log - Reader Handshake & Power Control Planning

**Date:** December 25, 2025
**Task:** Design comprehensive reader initialization and power monitoring system

## Objective

Replace passive error handling with active reader health verification. Implement handshake verification and power monitoring to provide precise failure diagnostics before attempting RFID operations.

---

## 1. Problem Analysis

### Current Limitations

The existing implementation produces only a warning when reader communication fails at startup. This passive approach has several issues:

| Problem                      | Impact                                            |
|------------------------------|---------------------------------------------------|
| No active verification       | Scanning attempted on unresponsive reader         |
| Ambiguous errors             | Cannot distinguish power vs communication failure |
| No remote diagnostics        | MQTT health reports lack reader status            |
| Manual intervention required | User must physically inspect hardware             |

### Solution Overview

Implement two-layer verification:
1. **Power rail sensing** - Hardware-level power status check
2. **Handshake verification** - Firmware communication test via `get_firmware_version` (0x72)
3. **State machine** - Structured state tracking with clear transitions

---

## 2. Handshake Verification Design

### Command Selection: `get_firmware_version` (0x72)

Selected the `get_firmware_version` command for handshake verification:

**Command Format:**
```
TX: [0xA0] [0x03] [0x01] [0x72] [Check]
RX: [0xA0] [0x05] [0x01] [0x72] [Major] [Minor] [Check]
```

**Rationale:**
- Lightweight command (no RF operations)
- Fast response (~10ms typical)
- Returns useful diagnostic info (firmware version)
- Documented in R300 Protocol V2.2, Section 2.1.3

### Verification Points

Handshake performed at three critical points:

| Trigger         | Purpose                                     |
|-----------------|---------------------------------------------|
| System startup  | Verify reader ready before configuration    |
| Power-on events | Confirm reader responsive after power cycle |
| Periodic (60s)  | Background health monitoring                |

## 3. Power Monitoring Architecture

### Experimental: Dual Power Rail Sensing with Relay

Initially experimented with dual-point power monitoring using a relay to distinguish between multiple failure modes:

```
Experimental Setup (Tested):
                    ┌──────────────┐
    3.3V Supply ────┤ GPIO 4 sense ├───┬─── Relay ───┬─── Reader Module
                    └──────────────┘   │             │
                             Aux Supply│     ┌───────┴────────┐
                               Sense   │     │ GPIO 27 sense  │
                                       │     │ (Reader Power) │
                                       │     └────────────────┘
                              ┌────────┴────────┐
                              │ GPIO 26 control │
                              └─────────────────┘
```

**Tested GPIO Configuration:**

| GPIO    | Function           | Purpose                   |
|---------|--------------------|---------------------------|
| GPIO 4  | Aux supply sense   | Monitor 3.3V before relay |
| GPIO 26 | Relay control      | Switch reader power       |
| GPIO 27 | Reader power sense | Monitor 3.3V after relay  |

### Mixed Results

The dual-sensing relay approach produced inconsistent behavior:

| Issue              | Observation                                       |
|--------------------|---------------------------------------------------|
| Contact bounce     | Intermittent false readings on power sense GPIO   |
| Timing sensitivity | Relay settle time varied, causing race conditions |
| Signal integrity   | Noisy readings on GPIO 27 during switching        |
| Complexity         | Three GPIO pins for marginal diagnostic benefit   |

### Decision: Revert to Single Power Check

After evaluating the experimental results, concluded that:

1. **Relay approach is problematic** - Mechanical switching introduces too many variables
2. **Transistor switching is better suited** - Solid-state, no bounce, faster, more reliable
3. **Single power check is sufficient** - GPIO 2 monitoring covers the primary use case

**Action taken:**
- Removed extra wiring for dual-sensing circuit
- Reverted to single power check on GPIO 2
- Ordered components for transistor-based design

### Planned: NPN Transistor Control

**Component ordered:** BC337 NPN transistor
- Collector current: 500mA (sufficient for reader)
- Switching speed: <100ns (vs relay ~10ms)
- Control: Active HIGH via GPIO 26

**Benefits over relay:**
- No contact bounce
- Deterministic switching time
- Lower power consumption
- More reliable long-term

### Current Configuration (Simplified)

```
    3.3V Supply ────┬─── Reader Module (always powered)
                    │
            ┌───────┴────────┐
            │ GPIO 2 sense   │ ← Single power rail check
            └────────────────┘
```

Transistor-controlled power switching will be implemented once parts arrive

## 4. State Machine Design

### Current Implementation (Simplified)

With single power check on GPIO 2, the current state machine uses:

```c
typedef enum {
    RFID_STATE_POWERED_OFF,           // Power rail down (GPIO 2 LOW)
    RFID_STATE_STARTUP_PENDING,       // Powered, waiting for boot
    RFID_STATE_RESPONSIVE,            // Handshake successful
    RFID_STATE_UNRESPONSIVE,          // Powered but no response
} rfid_state_t;
```

### Planned States (With Transistor Control)

Once transistor circuit is implemented, additional states will be added:

```c
typedef enum {
    RFID_STATE_SUPPLY_DOWN,           // Aux rail missing - hardware failure
    RFID_STATE_RELAY_CONTROL_ERROR,   // Transistor not switching correctly
    RFID_STATE_POWERED_OFF,           // Normal idle state
    RFID_STATE_STARTUP_PENDING,       // Powered, waiting for boot
    RFID_STATE_RESPONSIVE,            // Handshake successful
    RFID_STATE_UNRESPONSIVE,          // Powered but no response
} rfid_state_t;
```

                          ┌─────────────────┐
                          │ STARTUP_PENDING │ Grace period: 500ms

                                   │
                      ┌────────────┴────────────┐
                      │                         │
                      ▼                         ▼
            ┌─────────────────┐       ┌─────────────────┐

## 5. Diagnostic Matrix

### Current Diagnostics (Single Power Check)

| GPIO 2 | Handshake | State        | Diagnosis                  |
|--------|-----------|--------------|----------------------------|
| LOW    | -         | POWERED_OFF  | Reader power rail down     |
| HIGH   | Timeout   | UNRESPONSIVE | Powered but not responding |
| HIGH   | Success   | RESPONSIVE   | Reader healthy             |

### Planned Diagnostics (With Transistor)

| Aux Rail | Transistor | Reader Power | State                  | Diagnosis                |
|----------|------------|--------------|------------------------|--------------------------|
| LOW      | -          | -            | SUPPLY_DOWN            | Main 3.3V supply failure |
| HIGH     | ON         | LOW          | RELAY_CONTROL_ERROR    | Transistor not switching |
| HIGH     | OFF        | LOW          | POWERED_OFF            | Normal idle (expected)   |
| HIGH     | ON         | HIGH         | STARTUP_PENDING → test | Awaiting handshake       |

### Actionable Error Messages

```c
const char* rfid_state_to_string(rfid_state_t state) {
    switch (state) {
        case RFID_STATE_POWERED_OFF:
            return "Reader power off";
        case RFID_STATE_STARTUP_PENDING:
            return "Reader powering up, awaiting boot";
        case RFID_STATE_RESPONSIVE:
            return "Reader responsive";
        case RFID_STATE_UNRESPONSIVE:
            return "Reader powered but not responding";
        default:
            return "Unknown state";
    }
}
```

## 11. Lessons Learned

### Relay vs Transistor for Power Switching

| Aspect                   | Relay             | Transistor (BC337) |
|--------------------------|-------------------|--------------------|
| Switching speed          | ~10ms             | <100ns             |
| Contact bounce           | Yes (problematic) | None               |
| GPIO sensing reliability | Inconsistent      | Expected: stable   |
| Mechanical wear          | Yes               | None               |
| Power consumption        | Higher (coil)     | Lower              |
| Complexity               | Moderate          | Lower              |

**Conclusion:** For embedded power control with GPIO sensing, solid-state switching (transistor) is significantly more reliable than mechanical relays. The contact bounce and timing variability of relays made accurate power rail sensing impractical.
