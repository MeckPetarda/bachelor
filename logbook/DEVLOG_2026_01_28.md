# Development Log - MQTT Topic Standardization

**Date:** January 28, 2026
**Task:** Standardize MQTT topics across firmware and server, implement health/status tracking

## Objective

Unify MQTT topic structure between firmware and server using MAC-based device identification. Add infrastructure for health monitoring, connection tracking, and server-to-device configuration commands.

---

## 1. Topic Structure

Established hierarchical topic pattern using device MAC address as identifier:

```
attendance/lighthouse/{MAC}/
├── scans    - Tag detection events (QoS 2)
├── status   - Online/offline state (LWT)
├── health   - Consolidated health metrics (QoS 0)
└── config/+ - Configuration commands from server (QoS 1)
```

**MAC Format:** `AA:BB:CC:DD:EE:FF` (17 characters)

**Rationale:** MAC address is factory-programmed, globally unique, and retrievable without network connectivity. Eliminates need for manual device ID assignment.

**Reference:** ESP32 Technical Reference Manual Section 4.4 (eFuse Controller)

## 2. Server Implementation (Tasks 1–11)

### Topic Utilities

Created shared module with RegExp patterns for each topic type and utility functions:
- `extractMacAddress(topic)` - Extract MAC from any lighthouse topic
- `buildConfigTopic(mac, key)` - Construct config topic for publishing
- `buildStatusTopic(mac)` / `buildHealthTopic(mac)` / `buildScanTopic(mac)`

### Database Schema Updates

Added two new tables for telemetry persistence:

**`lighthouseHealthSnapshots`:**
- Stores periodic health reports (uptime, heap, WiFi RSSI, RFID state)
- Indexed by `(lighthouseId, recordedAt)` for efficient queries
- Retention cleanup removes records older than configured period

**`lighthouseConnectionEvents`:**
- Tracks online/offline transitions with timestamps
- Records `isGraceful` flag (distinguishes clean disconnect from LWT)
- Enables connection reliability analysis

### Message Handlers

Implemented dedicated handlers routed by topic pattern:

| Handler | Topic Pattern | Function                                                    |
|---------|---------------|-------------------------------------------------------------|
| Status  | `.../status`  | Updates runtime state, logs connection events               |
| Health  | `.../health`  | Parses JSON payload, stores snapshot, updates runtime state |
| Scan    | `.../scans`   | Existing functionality, refactored to use shared utilities  |

### Runtime State

Added in-memory state tracking for real-time dashboard access without database queries. Tracks connection status, last health metrics, and timestamps.

### Config Publisher

Created `publishConfig(mac, key, value)` function for server-to-device communication. Payload includes value and ISO timestamp. Used for future remote configuration (scan intervals, power settings, etc.).

### Retention Cleanup

Implemented automatic cleanup of old health snapshots and connection events based on configurable retention periods. Runs on server startup and daily thereafter.

## 3. Firmware Implementation (Tasks 12–14)

### MAC Address Retrieval

Replaced hardcoded client ID with factory-programmed MAC:

```c
uint8_t mac[6];
esp_efuse_mac_get_default(mac);
snprintf(s_device_mac, sizeof(s_device_mac),
         "%02X:%02X:%02X:%02X:%02X:%02X",
         mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
```

MAC string used as MQTT client ID and for dynamic topic construction.

**Reference:** `esp_efuse_mac_get_default()` retrieves MAC from eFuse block

### Dynamic Topic Building

Implemented `mqtt_client_get_topic(suffix)` function that constructs full topic path from base + MAC + suffix. Single static buffer (not reentrant) - caller must copy if needed.

### Consolidated Health Metrics

Refactored health publishing from multiple separate messages to single consolidated JSON payload:

```json
{
  "uptime_sec": 3600,
  "free_heap_bytes": 45000,
  "min_free_heap_bytes": 38000,
  "wifi_rssi_dbm": -52,
  "rfid": {
    "state": "RESPONSIVE",
    "is_responsive": true,
    "power_rail_present": true,
    "fw_version": "1.2",
    "last_error": 0
  }
}
```

Reduces MQTT overhead and simplifies server-side parsing.

### Config Message Parsing

Added stub handler for incoming config messages. Parses JSON payload, logs received key/value pairs. Actual setting application deferred to future task.
