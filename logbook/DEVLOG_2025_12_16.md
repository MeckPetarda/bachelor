# Development Log - Y300 UHF RFID Reader Integration

**Date:** December 16, 2024  
**Task:** Integrate Y300 UHF RFID reader module with ESP32 via UART  
**Status:** ✓ Complete - Communication established, protocol implemented

## Objective

Integrate Y300 (R300-based) UHF RFID reader module with ESP32 via UART2 for real-time contactless tag detection. Module provides 2-3 meter range for hands-free attendance tracking.

## Initial Problem

ESP32 successfully transmitted commands to Y300 (reset command triggered audible beep), but received zero bytes in response. UART configuration appeared correct but no data appeared in receive buffer.

## Solution Process

### 1. Protocol Correction
Initial implementation used incorrect protocol assumptions. Consulted R300 specification (R300_UHF_RFID_reader_module_protocol_.pdf V2.2):

**Corrected from:**
- Frame header: `0xBB 0xBB` → `0xA0`
- Checksum: CRC16 → Simple sum `(~sum) + 1`
- Baud rate: 9600 → 115200 bps

**Correct frame format:** `[0xA0][Len][Addr][Cmd][Data...][Check]`

### 2. Hardware Fix
Created comprehensive UART RX diagnostic tool that revealed **zero bytes received** across all read strategies - indicated hardware-level issue, not software.

**Root cause:** Wiring error in physical connections  
**Fix:** Corrected Y300-to-ESP32 wiring with proper TX/RX mapping and common ground

**Result:** Reset command immediately worked (audible beep) and UART RX buffer successfully received data.

## Implementation

### Hardware Configuration
```
Y300 TX  → ESP32 GPIO16 (UART2 RX)
Y300 RX  → ESP32 GPIO17 (UART2 TX)
Y300 GND → ESP32 GND (common ground)
```

### Commands Implemented
1. **Reset (0x70)**
   - Initializes module (audible beep confirms receipt)
   - No response data (by design)

2. **Firmware info query (0x72)**
   - Get the version of firmware running on device

3. **Real-Time Inventory (0x89)**
   - Continuous tag scanning mode

### Software Architecture
- Background UART RX task processes incoming frames
- Callback-based design for tag detection events
- Thread-safe statistics tracking (mutex-protected)
- Frame parsing with checksum validation
- Integrated with existing GPIO system (buttons, LEDs, PIR sensor)

## Technical Notes

### Protocol Details
- Frame header: Single byte `0xA0` (not two-byte sync)
- Checksum algorithm: `(~sum_of_bytes) + 1` per section 6, page 43
- Default baud rate: 115200 bps per section 1.1
- Real-time inventory streams tags immediately (not buffered)

### Hardware Considerations
- UART2 selected for GPIO16/17 - no conflicts with console or strapping pins
- ESP32 TRM Section 7.8 confirms UART2 availability
- Common ground connection critical for reliable communication
- Wiring verification essential before debugging protocol

### Tag Data Structure
Response includes:
- EPC (Electronic Product Code) - variable length tag ID
- RSSI (Received Signal Strength Indicator)
- Antenna ID (which antenna detected the tag)
- Frequency parameter
- Protocol Control bytes

## Lessons Learned

1. **Protocol verification first** - Consulting specification document immediately would have saved hours of debugging with wrong frame format
2. **Hardware diagnostics essential** - Comprehensive RX test tool quickly revealed zero-byte reception issue, shifting focus to wiring
3. **Incremental validation effective** - Testing reset command first (simplest, most reliable) confirmed basic communication before proceeding to complex inventory mode
4. **Documentation accuracy** - R300 specification PDF was authoritative and accurate, unlike generic protocol assumptions

## Key Takeaways

- Y300/R300 uses simple, efficient protocol (single-byte header, basic checksum)
- UART2 is reliable choice for ESP32 peripheral communication (GPIO16/17)
- Physical wiring errors can mask software issues - test hardware layer first
- Real-time inventory mode (0x89) optimal for single-tag attendance scenarios
- Callback architecture keeps tag processing separate from UART handling
