# Development Log - Captive Portal & Setup Page Enhancements

**Date:** January 24–27, 2026
**Task:** Implement captive portal, external HTML serving, reliable message delivery, and MQTT configuration

## Objective

Improve the setup experience with automatic captive portal detection, move HTML out of C source code for maintainability, implement reliable browser-to-device message acknowledgment, and extend configuration to include MQTT broker settings.

---

## 1. Captive Portal Implementation

### Problem

Users had to manually navigate to `http://192.168.4.1` after connecting to the setup AP. Mobile devices and computers perform connectivity checks but weren't being redirected to the setup page.

### Solution

Implemented a lightweight DNS server that resolves all domain queries to the ESP32's IP (192.168.4.1), combined with HTTP wildcard handler for 302 redirects.

**DNS Server Behavior:**
- Binds to UDP port 53
- Responds to any A record query with 192.168.4.1
- TTL set to 60 seconds
- Runs in dedicated FreeRTOS task during AP mode

**HTTP Wildcard Handler:**
- Catches all GET requests not matching specific routes (`/`, `/configure`, `/restart`, `/ack`)
- Returns HTTP 302 redirect to `http://192.168.4.1/`
- Registered last to ensure specific handlers take priority

**Platform Detection Results:**

| Platform | Behavior                                                 |
|----------|----------------------------------------------------------|
| iOS      | Safari opens automatically                               |
| Android  | "Sign in to network" notification appears                |
| Windows  | "Sign in to this network" popup                          |
| macOS    | Safari opens automatically                               |
| Linux    | Manual navigation required (no captive portal detection) |

## 2. SPIFFS-Based HTML Serving

### Problem

Setup page HTML was embedded as string literals in C source code, making frontend changes require recompilation and mixing concerns.

### Solution

Moved HTML/CSS/JavaScript to external file served from SPIFFS filesystem.

**Partition Layout:**
- Added `spiffs` partition (448KB at offset 0x292000)
- Build system compiles `spiffs_image/` directory into firmware
- HTML file loaded and served in 512-byte chunks to minimize RAM usage

**Benefits:**
- Frontend editable without C knowledge
- HTML previewable in browser during development
- CSS/JS changes don't require firmware recompilation
- Cleaner separation of concerns

**Reference:** `tasks/setup_page_addendum.md` Part 1

## 3. Browser Acknowledgment System

### Problem

After credential submission, the ESP32 would send a result and potentially restart before the browser displayed the message. Network hiccups could cause users to miss success/error feedback.

### Solution

Implemented two-way acknowledgment protocol:

1. Browser submits credentials via POST `/configure`
2. ESP32 tests connection, returns JSON result
3. Browser displays result to user
4. Browser sends POST `/ack` with unique message ID
5. ESP32 confirms acknowledgment received via semaphore
6. Only then does restart button become active

**Timeout Protection:**
- ESP32 waits maximum 10 seconds for acknowledgment
- If no acknowledgment received, continues without restart
- Prevents device from hanging if browser disconnects

**Message ID Validation:**
- Each result includes unique ID
- Acknowledgment must include matching ID
- Prevents stale acknowledgments from affecting new submissions

**Reference:** `tasks/setup_page_addendum.md` Part 2

## 4. MQTT Broker Configuration

### Problem

MQTT broker address was hardcoded at compile time, requiring firmware rebuild to change broker.

### Solution

Extended setup page and NVS storage to include MQTT configuration.

**New Form Fields:**
- MQTT Broker IP (IPv4, pre-filled with default)
- MQTT Broker Port (1-65535, default 1883)

**Storage:**
- Generalized `wifi_settings_storage` to `settings_storage`
- Added NVS keys: `mqtt_ip` (string, max 15 chars), `mqtt_port` (uint16_t)
- Defaults written on first boot if keys missing

**Validation:**
- Client-side: IPv4 regex pattern, port range check
- Server-side: `inet_aton()` for IP validation

**Test Flow:**
- Separate "Test WiFi" and "Test MQTT" buttons
- MQTT test enabled only after WiFi test passes
- MQTT connection attempt with 5-second timeout
- Failure warns but doesn't block device operation

**Reference:** `tasks/mqtt_setup.md`
