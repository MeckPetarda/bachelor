# Task: MQTT Scan Event Batching and QoS Reduction for Live Tag Events

**Purpose:** During active RFID scanning the firmware produces ~28+ individual MQTT publishes in under 4 seconds for a single tag. Each publish uses QoS 2, which requires a four-way handshake (PUBLISH → PUBREC → PUBREL → PUBCOMP). This volume of concurrent QoS 2 handshakes saturates the Aedes broker, which responds with a TCP RST (errno 104, ECONNRESET), dropping the connection. The fix has two parts: (1) reduce the live scan publish path to QoS 1, eliminating the handshake overhead; (2) introduce a time-windowed batch accumulator on the firmware that collects raw detections over a configurable interval and publishes them as a single JSON array, reducing publish rate without discarding any data. The server scan handler must be updated to accept the new array-always payload format.

**Files to modify:**
- `src/lighthouse/main/my_mqtt_client.h`
- `src/lighthouse/main/my_mqtt_client.c`
- `src/lighthouse/components/wifi_provisioning/settings_storage.h`
- `src/lighthouse/components/wifi_provisioning/settings_storage.c`
- `src/server/src/mqtt/handlers/scan.ts`

**Files NOT to modify:** `src/lighthouse/main/lighthouse.c`, `src/lighthouse/main/io_controller.c`, `src/lighthouse/main/rfid_reader.c`, `src/lighthouse/main/offline_event_logger.c`, `src/lighthouse/main/offline_event_logger.h`. The tag detection callback and offline logger interfaces are unchanged. All other server files are unchanged.

---

## Overview / Context

### Root cause (confirmed from serial log analysis)

The dropout occurs at the TCP transport layer with `errno 104 (ECONNRESET)` — the broker actively closes the connection. This is not an outbox-full condition (the `-2` return from `esp_mqtt_client_enqueue` is never logged). The cause is the volume of concurrent QoS 2 handshakes generated by back-to-back tag detections during an active `0x89` real-time inventory scan window.

The firmware currently calls `mqtt_client_publish_tag_event()` once per tag detection callback. With `0x89` real-time inventory at 10ms inter-round intervals, a 5-second scan window for a single tag in range produces 20–60 individual publishes. At QoS 2, each publish generates 4 MQTT control packets, resulting in 80–240 control packets in 5 seconds. Aedes cannot drain this backlog and issues RST.

### Architecture decision

Raw scan data must not be deduplicated or suppressed. Both direction detection algorithms (temporal centroid and RSSI-weighted centroid) require the full set of timestamped RSSI readings from each lighthouse. Suppressing any detection would corrupt the input signal.

The solution is to accumulate raw detections in a fixed in-memory ring buffer during the scan window and flush them as a single JSON array on a repeating timer. This reduces publish rate from one-per-detection (~10 publishes/second peak) to one-per-batch-window (6–10 publishes/second → ~7 publishes/second at 150ms). Each element in the batch array retains its original EPC, RSSI, antenna, frequency, and `timestampMs`.

### QoS decision

`MQTT_QOS_TAG_EVENTS` is defined as `2` and is referenced in two call sites:
- `esp_mqtt_client_enqueue()` in `mqtt_client_publish_tag_event()` — the **live** path. This must change to QoS 1.
- `esp_mqtt_client_publish()` in `replay_offline_event()` — the **replay** path. This must remain QoS 2.

The constant value must not change. The live enqueue call must use a new dedicated constant `MQTT_QOS_TAG_EVENTS_LIVE` defined as `1`.

### Payload format change

The server currently expects a single JSON object per MQTT message on the `scans` topic. The new format is always a JSON array, even when it contains a single element. This applies to both the live batch path and the offline replay path. The server handler must be updated accordingly. This is a breaking protocol change — both sides must be updated together.

## Part A — Firmware

### Step A.1: Add `MQTT_QOS_TAG_EVENTS_LIVE` constant to `my_mqtt_client.h`

In `my_mqtt_client.h`, find the existing QoS constant definitions:
```c
#define MQTT_QOS_TAG_EVENTS      2 // QoS 2: Exactly Once
#define MQTT_QOS_HEALTH_METRICS  0 // QoS 0: At Most Once
#define MQTT_QOS_CONFIG_COMMANDS 1 // QoS 1: At Least Once
```

Add immediately after `MQTT_QOS_TAG_EVENTS`:
```c
#define MQTT_QOS_TAG_EVENTS_LIVE 1 // QoS 1: At Least Once (live scan path only)
```

Do not change the value of `MQTT_QOS_TAG_EVENTS`. The replay path continues to use it at QoS 2.

Also add the following compile-time default in the configuration section of the header:
```c
#define MQTT_SCAN_BATCH_INTERVAL_MS_DEFAULT 150
#define MQTT_SCAN_BATCH_MAX_ENTRIES         64
```

`MQTT_SCAN_BATCH_MAX_ENTRIES` is the maximum number of raw detections that can accumulate within one batch window before the buffer is full. 64 is a safe upper bound — at 10ms rounds, a 150ms window yields at most ~15 detections under normal conditions. If the buffer fills before the timer fires, the batch is flushed immediately (see Step A.3).

### Step A.2: Add NVS load/save for `scan_batch_ms` to `settings_storage`

#### `settings_storage.h`

Add the NVS key constant and a new load/save API for the batch interval. Place these alongside the existing MQTT configuration definitions and functions.

Add constant:
```c
#define MQTT_DEFAULT_SCAN_BATCH_MS 150
```

Add two function declarations:
```c
settings_storage_error_t scan_batch_settings_load(uint32_t *batch_ms);
settings_storage_error_t scan_batch_settings_save(uint32_t batch_ms);
```

#### `settings_storage.c`

Add the NVS key string as a `static const char *` alongside the existing key definitions:
```c
#define NVS_SCAN_BATCH_MS_KEY "scan_batch_ms"
```

Implement `scan_batch_settings_load()`:
- Open the same NVS namespace as `mqtt_settings_load` (uses `settings_storage_nvs_handle`).
- Read a `uint32_t` for key `NVS_SCAN_BATCH_MS_KEY` using `nvs_get_u32()`.
- If `ESP_ERR_NVS_NOT_FOUND`, populate `*batch_ms` with `MQTT_DEFAULT_SCAN_BATCH_MS` and return `SETTINGS_STORAGE_OK`.
- Validate: clamp to range 50–2000ms. Values outside this range are clamped silently and a warning is logged.
- Return `SETTINGS_STORAGE_OK` on success.

Implement `scan_batch_settings_save()`:
- Validate input is within 50–2000ms. Return `SETTINGS_STORAGE_INVALID_PARAM` if not.
- Write using `nvs_set_u32()` with key `NVS_SCAN_BATCH_MS_KEY`.
- Call `nvs_commit()`.
- Return `SETTINGS_STORAGE_OK` on success, `SETTINGS_STORAGE_WRITE_ERROR` on failure.

Follow the exact same pattern as `mqtt_settings_load()` / `mqtt_settings_save()` in the same file.

### Step A.3: Replace single-event publish with batch accumulator in `my_mqtt_client.c`

This is the core change. The existing `mqtt_client_publish_tag_event()` function is the entry point called from `on_tag_detected()` in `lighthouse.c` with `offline=false` for live events. Its signature must not change.

#### A.3.1 — Module-level state

Add the following static state near the top of `my_mqtt_client.c` alongside existing static variables:

- A fixed-size array of `rfid_tag_event_t` named `s_batch_entries` with size `MQTT_SCAN_BATCH_MAX_ENTRIES`.
- A `uint32_t s_batch_count` initialised to 0.
- A `SemaphoreHandle_t s_batch_mutex` for thread safety between the tag detection callback (UART RX task) and the timer callback (timer task).
- A `esp_timer_handle_t s_batch_timer`.
- A `uint32_t s_batch_interval_ms` loaded from NVS on init.

#### A.3.2 — Batch flush function (static)

Add a static function `flush_scan_batch()` with no parameters and no return value. This function:

1. Takes `s_batch_mutex`.
2. If `s_batch_count == 0`, releases mutex and returns immediately.
3. Builds a JSON array string. Each element has the same fields as the current single-event payload: `epc`, `timestampMs`, `rssiDbm`, `antennaId`, `frequency`, `deviceId`, `offline` (always `false` for live), `timeBasis`. No `replayTime` field on live events.
4. Releases `s_batch_mutex` before calling into the MQTT stack (do not hold the mutex while calling `esp_mqtt_client_enqueue`).
5. Calls `esp_mqtt_client_enqueue()` with `MQTT_QOS_TAG_EVENTS_LIVE` (QoS 1), `store_in_outbox=true`.
6. Handles `-2` (outbox full) and `< 0` (error) the same way as the existing code.
7. Resets `s_batch_count` to 0 after successful or failed enqueue (do not accumulate across failed flushes).

For the JSON array construction, use a statically allocated buffer. Size it conservatively: each entry is at most ~200 bytes, so `MQTT_SCAN_BATCH_MAX_ENTRIES * 200 + 32` bytes for the array wrapper. This is approximately 13KB. If the formatted length would exceed the buffer, truncate the array at the last safely fitting entry, log a warning, and publish the truncated batch. Do not use heap allocation.

The `timeBasis` field for each entry is derived identically to the existing single-event logic: call `time_sync_get_quality()` and map to `"synced"`, `"estimated"`, or `"relative"`.

#### A.3.3 — Timer callback

Add a static timer callback `batch_timer_callback(void *arg)` that simply calls `flush_scan_batch()`. This runs in the ESP timer task context, which is a high-priority task — `flush_scan_batch()` must not block for extended periods. The mutex acquisition is bounded and the MQTT enqueue is non-blocking, so this is acceptable.

#### A.3.4 — Modify `mqtt_client_publish_tag_event()` for live path

The existing function handles both live (`offline=false`) and replay (`offline=true`) events. Split the behaviour:

**For `offline=true`** (replay path): behaviour is entirely unchanged. The function builds a single-element JSON array (see Step A.4 for format) and calls `esp_mqtt_client_publish()` with `MQTT_QOS_TAG_EVENTS` (QoS 2) as before. The only change is wrapping the payload in `[...]`.

**For `offline=false`** (live path): instead of publishing immediately, the function:
1. Takes `s_batch_mutex`.
2. If `s_batch_count < MQTT_SCAN_BATCH_MAX_ENTRIES`, copies the `rfid_tag_event_t` into `s_batch_entries[s_batch_count]` and increments `s_batch_count`.
3. If `s_batch_count == MQTT_SCAN_BATCH_MAX_ENTRIES` (buffer full), releases mutex and calls `flush_scan_batch()` immediately, then re-acquires mutex to add the current event (which now fits in the cleared buffer).
4. Releases mutex.
5. Returns `ESP_OK`. The batch timer will handle the actual publish.

The early-exit guards (null check, connection check) remain at the top of the function before the branch.

#### A.3.5 — Initialise batch timer in `mqtt_client_init()`

After the MQTT client is started (after `esp_mqtt_client_start()`), add:

1. Call `scan_batch_settings_load(&s_batch_interval_ms)` to load the configured interval from NVS.
2. Initialise `s_batch_mutex` with `xSemaphoreCreateMutex()`.
3. Create a periodic ESP timer using `esp_timer_create()` with `batch_timer_callback` as the callback and the tag string `"scan_batch"`.
4. Start the timer with `esp_timer_start_periodic()` using `s_batch_interval_ms * 1000` (convert ms to µs).

Log the loaded interval at INFO level: `"Scan batch interval: %lu ms"`.

If `esp_timer_create()` or `esp_timer_start_periodic()` fails, log an error and return `ESP_FAIL`. This is a hard initialisation failure.

## Part B — Server

### Step B.1: Update `handleScanMessage` in `src/server/src/mqtt/handlers/scan.ts`

The payload is now always a JSON array. Each element has the same fields as the previous single-object payload.

#### B.1.1 — Update `ScanPayload` type

Rename the existing `ScanPayload` interface to `ScanEntry` (it describes one element). Add a new type alias:
```typescript
type ScanPayload = ScanEntry[];
```

#### B.1.2 — Update `validatePayload`

Rename to `validateEntry` and keep its logic unchanged — it validates one `ScanEntry` object.

Add a new `validatePayload(payload: unknown): payload is ScanPayload` function that:
- Checks `Array.isArray(payload)` and that `payload.length > 0`.
- Returns false if not an array or empty.
- Does **not** validate individual entries here — that is done per-entry in the loop below.

#### B.1.3 — Update `handleScanMessage` processing loop

After JSON parsing and array validation, iterate over each element in the array. For each element:
- Call `validateEntry()`. If invalid, log a warning with the element index and skip that element — do not abort the entire batch.
- Run the existing lighthouse lookup, timestamp resolution, DB insert, and WebSocket broadcast logic unchanged, applied to that element.

The lighthouse lookup (`macAddress` extraction from topic) happens once per message, before the loop — it is the same for all elements in a batch since they originate from the same device.

The per-element DB insert and WebSocket emit are identical to the current single-event logic. Do not batch the DB inserts — insert each element individually inside the loop to preserve existing error handling and scan ID assignment behaviour.

- [ ] `idf.py build` completes without errors or new warnings.
- [ ] On boot, serial log shows `Scan batch interval: 150 ms` (or the NVS-stored value if previously overridden).
- [ ] During an active scan window, the serial log shows `Published tag event batch` (or equivalent batch-flush log) at approximately 150ms intervals, not once per tag detection.
- [ ] The number of `Published tag event` log lines during a 5-second scan window is ≤ 34 (5000ms / 150ms = ~33 flushes), not 20–60.
- [ ] No `poll_write select error 104` (ECONNRESET) or `Writing failed: errno=119` errors appear during or after a scan window.
- [ ] `MQTT_EVENT_DISCONNECTED` is not triggered during normal scanning operation.
- [ ] Offline replay log continues to show individual event replay lines with `timeBasis=synced` — replay behaviour is unchanged.
- [ ] Server-side: each element of an incoming batch array produces one row in `raw_scans` and one WebSocket broadcast. A batch of N detections produces exactly N rows.
- [ ] A malformed element within a batch does not prevent valid elements in the same batch from being processed.
- [ ] `MQTT_QOS_TAG_EVENTS` remains defined as `2`. Only `MQTT_QOS_TAG_EVENTS_LIVE` is `1`. The replay path continues to call `esp_mqtt_client_publish` with `MQTT_QOS_TAG_EVENTS`.
- [ ] `scan_batch_settings_load()` returns `MQTT_DEFAULT_SCAN_BATCH_MS` (150) when no NVS key exists (first boot).
- [ ] TypeScript server compiles without errors after handler changes.
